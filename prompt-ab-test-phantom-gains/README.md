# You Pinned Everything and the Score Still Moved

Companion code for the article. Brief: `topics/prompt-ab-test-phantom-gains.md`.

## The question

Pin the model, the provider, the questions and `temperature=0`. Rerun. Does the
score come back the same?

## The answer

No. Measured on 100 tool-calling questions against
`deepseek/deepseek-v4-flash-0731` on OpenRouter, 2026-09-12 to 2026-09-14:

| Quantity | Value |
| --- | ---: |
| One pinned provider, same 100 questions, `temperature=0`, three runs | **79, 82, 79** |
| Run-to-run movement, median provider / worst provider | **3 / 6 questions** |
| Five providers, best mean minus worst | **2.0** |
| Prompt effect, provider pinned | **+1.3** |
| Unpinned A/B gap, three identical runs | **−2.0 / +0.0 / +1.0** |

Pin the model, the provider, `temperature=0` and the questions, rerun, and the
score still moves three questions. That is more than the prompt edit was worth.

## How to rerun it

Needs `OPENROUTER_API_KEY` in the repo root `.env` and about $0.40 of credit. The
recorded run is 2,900 requests and cost $0.38.

```bash
python3 scripts/build_cases.py                 # writes cases.jsonl (100 cases)
python3 scripts/run.py sweep    --repeat 0     # 6 providers x 100 cases, prompt A
python3 scripts/run.py pinned   --repeat 0     # prompt B, pinned to one provider
python3 scripts/run.py unpinned --repeat 0     # both prompts, no provider block
# repeat each with --repeat 1 and --repeat 2; analyze.py reads runs 0 to 2
python3 scripts/score.py                       # scores results.jsonl in place
python3 scripts/analyze.py                     # every table in the article
```

`scripts/score.py` run with no arguments also re-scores, so a scoring change can
be applied to recorded results without re-issuing requests.

## One worked example, end to end

Question `live_multiple_489-147-4` asks to book a train ticket from New York to
Phoenix, leaving at 13:45. The ground truth wants `journey_start_time` filled.

Same provider, same question, `temperature=0`, three runs:

```
run 0   wrong     Trains_1_GetTrainTickets(..., number_of_adults)
run 1   correct   Trains_1_GetTrainTickets(..., journey_start_time)
run 2   correct   Trains_1_GetTrainTickets(..., journey_start_time)
```

Two plausible next fields and nothing in the request decides between them. The
model is batched with whatever other traffic is arriving, GPU kernels sum in
different orders at different batch sizes, float addition is not associative,
and `argmax` flips when two tokens are close. Between 3 and 12 questions per 100
move this way on any given provider.

## Files

| File | What it holds |
| --- | --- |
| `scripts/build_cases.py` | Pulls cases from BFCL V4 and rewrites their schemas into OpenAI tools format |
| `scripts/run.py` | Issues every request, pins or does not, records who served it |
| `scripts/score.py` | AST-style match against BFCL ground truth |
| `scripts/analyze.py` | Provider spread, endpoint noise, prompt effect, and the eval-sizing bootstrap |
| `cases.jsonl` | The 100 questions with their ground truth |
| `quoted-examples.json` | The ten raw responses the article quotes, grouped by what each shows |
| `results.jsonl` | 2,300 scored rows |
| `transcripts/` | Raw response bodies, one per request. Not committed, regenerated by a rerun |

## Terms used above

- **Model**: the weights. One artifact, published once.
- **Provider**: a company serving those weights on its own GPUs, at its own
  precision, with its own serving stack. 28 of them serve this model.
- **Pinned**: `provider: {only: [...], allow_fallbacks: false}`. Without
  `allow_fallbacks: false`, `only` is a preference and a busy provider silently
  hands the request elsewhere.
- **Endpoint noise**: the same pinned provider returning a different answer to
  an identical request. Happens at `temperature=0` because serving kernels are
  not batch-invariant and batch size follows server load.

## Results held back from the article

The article ships one finding. These came out of the same runs and are recorded
here rather than stacked into it.

- **`coreweave/fp8` rejects any function name containing a dot**, with
  `400 Validation: Function at index 0 has an invalid name`. Five other
  providers accept the identical request. Excluded from the scored set because
  its eligibility differs, not its quality.
- **One provider was measurably worse.** `wafer/fast` scored 77.0 against 80 to
  82 for the other five, on all three runs, while declaring nothing unusual and
  costing more than four providers that beat it. Nothing published predicts it:
  `relace/fp4` declares the lowest precision and beats both fp8 providers.
- **Mean and stability look like separate properties.** `digitalocean` had the
  highest mean (82.0) and the widest run-to-run range (6). `relace/fp4` was
  mid-pack on mean and the steadiest (range 2). Six providers is not enough to
  claim a relationship.
- **The gateway default matched the best pinned provider.** Unpinned scored
  82, 82, 82, drawing only Relace and DeepInfra. Whether default routing
  reliably avoids a weak provider, three runs cannot say.
- **A discarded first case set.** 45 questions from `simple_python` and
  `multiple` put every provider at 8 to 10 out of 10. The ceiling left nothing
  to measure, and the small sample inflated everything: provider spread read
  14 points at n=20 against 5 at n=100. Rebuilt on `live_multiple` instead.
- **`results.jsonl` holds more runs than the analysis uses.** `deepinfra/fp8`
  has five sweep runs, picked up while patching a credit failure mid-experiment.
  `analyze.py` reads runs 0 to 2 for every condition, so no provider is measured
  more precisely than the rest. Nothing was deleted.
